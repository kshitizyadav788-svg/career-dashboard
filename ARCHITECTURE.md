# Architecture — How the Career Dashboard is Built (plain-language)

This explains what the project is made of and how the pieces fit, in language a **non-technical**
reader can follow, with enough detail for a **technical** reader too.

---

## 1. The one-paragraph version
It's a **website with no server**. The whole dashboard is a single HTML file hosted for free on
GitHub Pages. A **robot that runs every hour in the cloud** (a GitHub Action) fetches fresh jobs and
saves them into a file the website reads. Resumes are generated by **small Python scripts** on the
Mac that produce Word + PDF files. There is no database and no login — data files in the GitHub
repository ARE the database, and GitHub is the single source of truth.

Think of it like a **noticeboard (the website)**, a **clock-triggered assistant that pins fresh job
ads to it every hour (the Action)**, and a **printing machine that makes tailored resumes on demand
(the Python scripts)**.

## 2. Tech stack at a glance
| Layer | Technology | Why |
|-------|-----------|-----|
| Website (UI) | **Plain HTML + CSS + vanilla JavaScript**, one file (`index.html`) | No framework needed; loads instantly; easy to host free. |
| Hosting | **GitHub Pages** (static hosting) | Free, public, zero servers to manage. |
| Automation | **GitHub Actions** (cron, hourly) | Free cloud scheduler; runs the job fetch without a laptop. |
| Job data | **JSearch API + Adzuna API** → `jobs.json` | Two job sources merged into one scored feed. |
| Resume engine | **Python 3** + `python-docx` (write Word) + `pypdf` (measure PDF) | Generates `.docx` from a data dict. |
| PDF + page-fit | **LibreOffice** (`soffice`) headless docx→PDF; **poppler** (`pdftoppm`) to preview | Only a real layout engine can measure true page count/fill. |
| Data storage | **JSON files in the Git repo** (`jobs.json`, `seed_jobs.json`, `external_resumes.json`) | No database; Git history = audit trail. |
| Per-device state | Browser **localStorage** | Tracking (applications, tailor queue) saved per device. |
| Profiles (external) | **Claude-in-Chrome** browser automation | Updates Naukri / Foundit / iimjobs live (not in this repo). |

## 3. The three moving parts

### Part A — The website (`index.html`)
- A **single-page app** written in plain JS (no React/Vue). Everything — tabs, tables, scoring,
  rendering — is in this one file.
- On load it **fetches `jobs.json` and `external_resumes.json`** and renders them. If opened locally
  as a `file://`, it falls back to baked-in seed data.
- Client-side `score()` / `locBonus()` re-rank jobs (Gurugram +8, Bangalore +5) so the best-fit,
  best-location roles float to the top.

### Part B — The hourly job robot (`.github/workflows/refresh-jobs.yml` → `fetch_jobs.py`)
Runs every hour in GitHub's cloud:
1. Calls **JSearch** and **Adzuna** APIs (keys stored as GitHub repo secrets).
2. `score_fit()` scores each job: `fit*0.4 + comp*0.2 + growth*0.2 + prob*0.2` + a location bonus.
3. `merge_jobs()` merges the fresh feed with `seed_jobs.json` (curated/Naukri roles that have no
   API), de-dupes, and drops entries with no URL.
4. `write_jobs_json()` writes `jobs.json` and the Action **commits it back to the repo**.
5. The live site picks it up automatically.

### Part C — The resume factory (`build_resume.py` + `build_cover_letter.py`)
- `DATA` — a Python dict holding all of Kshitiz's real resume content (summary, experience groups,
  bullets, skills, education).
- `render(data, out, style)` — turns the dict into a styled one-page Word doc.
- `fit_to_page(data, out)` — the important one: renders the docx, converts to PDF via LibreOffice,
  **measures the real page count and how far the text reaches down the page**, and automatically
  picks the loosest font/line-spacing preset (kept in the ATS-safe 9.5–11pt band) that fills exactly
  ONE page cleanly. This is why every resume is one full page with no dead space and never spills
  over. It writes both `.docx` and `.pdf`.
- `keyword_coverage_score(data, keywords)` — computes the honest match % against a hand-curated
  must-have keyword list.
- `build_cover_letter.py` — renders a matching one-page cover letter, reusing the resume's fonts/colors.

## 4. Data flow (in words)
```
Job discovery:
  JSearch API ─┐
               ├─► fetch_jobs.py (score + merge) ─► jobs.json ─► index.html (Job Matches tab)
  Adzuna API ──┘        ▲
  seed_jobs.json ───────┘  (curated / Naukri roles, no API)

Resume tailoring (pasted JD):
  User pastes JD in chat ─► Claude extracts real must-haves
    ─► tailors a copy of build_resume.DATA (real content only, + experience_bank.md)
    ─► keyword_coverage_score() = honest %
    ─► fit_to_page() = one full page (docx + pdf)
    ─► append entry to external_resumes.json ─► git push
    ─► index.html (External JD Resumes tab)
```

## 6. Why it's built this way (design decisions)
- **No server / no database:** cheapest, simplest, and Git gives a free audit trail + cross-device sync.
- **Static site + hourly Action:** jobs stay fresh without any machine being on.
- **LibreOffice for page-fit:** python-docx alone cannot know rendered page count or fill — only a
  real layout engine can — so the one-page guarantee depends on `soffice` being installed.
- **Manual (Claude-driven) tailoring:** full automation was tried and hit real cost/quota walls;
  the manual route keeps the honesty bar high, which is the whole point.

## 7. Setup on a fresh Mac (one time)
```bash
python3 -m venv .venv && .venv/bin/pip install python-docx pypdf
brew install --cask libreoffice && brew install poppler
.venv/bin/python build_resume.py   # builds the master resume, auto-fit to one full page
```
Windows: has its own python-docx; install LibreOffice for `fit_to_page`, or use Word to check pages.
Job fetch (optional locally): `pip install requests` then run `fetch_jobs.py` with the API keys.
